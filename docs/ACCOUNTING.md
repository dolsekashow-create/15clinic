# نموذج المحاسبة

## لماذا قيد مزدوج

النموذج البسيط (جدول إيرادات + جدول مصروفات) ينهار عند أول متطلب حقيقي: مرتجع، دفعة جزئية، ضريبة، تحصيل تأمين، تحويل بين الفروع. القيد المزدوج هو النموذج الوحيد الذي يستوعب هذا كله بلا إعادة كتابة، وهو ما يتوقعه أي مراجع حسابات.

كل شيء **بيانات وليس كودًا**: شجرة الحسابات، نسب الضريبة، وربط الحسابات الآلية كلها قابلة للتعديل من الواجهة بعد اجتماع المتطلبات.

## الثوابت المفروضة في `AccountingService`

1. كل قيد مُرحَّل متوازن: مجموع المدين = مجموع الدائن بالضبط.
2. القيد المُرحَّل غير قابل للتعديل. التصحيح = قيد عكسي (`reverseEntry`)، والاثنان يبقيان ظاهرين للمراجع.
3. لا ترحيل داخل فترة مقفلة.
4. الحسابات التجميعية (Group) لا يُرحَّل عليها.
5. كل قيد آلي يحمل `sourceType` و`sourceId` — أي رقم في أي تقرير يمكن تتبعه للمستند الذي أنتجه.

## المبالغ

أعداد صحيحة بالقروش (`Minor`)، ونسب الضريبة بالـbasis points (1400 = 14%).
السبب: `0.1 + 0.2 !== 0.3`. أي `float` في دفتر الأستاذ سيُكتشف لاحقًا كفروق قروش لا يستطيع أحد تفسيرها.

## القيود الآلية

**إصدار فاتورة**

```
مدين   ذمم العملاء              إجمالي الفاتورة
مدين   خصومات ومسموحات          قيمة الخصم
    دائن   إيرادات الخدمات       القيمة قبل الخصم (لكل سطر، بحساب الخدمة أو الافتراضي)
    دائن   ضرائب مستحقة          قيمة الضريبة
```

الإيراد يُقيَّد بالقيمة قبل الخصم، والخصم يُقيَّد في حساب مقابل مستقل — حتى يظل «ما طلبناه» و«ما تنازلنا عنه» رقمين منفصلين بدل رقم واحد مُصفّى.

**تحصيل دفعة**

```
مدين   الخزينة / البنك / بطاقات تحت التحصيل     المبلغ
    دائن   ذمم العملاء                          المبلغ
```

حساب المدين يُختار حسب طريقة الدفع؛ مدفوعات البطاقات تدخل حساب «تحت التحصيل» لأن المال لم يصل البنك بعد فعليًا.

**إلغاء فاتورة** — يُرفض إن كان عليها تحصيلات؛ وإلا يُنشأ قيد عكسي للقيد الأصلي.

## غير محدد بعد — `BUSINESS_RULE_PENDING`

هذه لم تُخترع، وكلٌّ منها يدخل كأسطر قيد إضافية دون تغيير في الـSchema:

- المعالجة الضريبية للخدمات الطبية (النسب، الإعفاءات، الخصم تحت حساب الضريبة)
- عمولات الأطباء / اقتسام الإيراد
- دورة فوترة شركات التأمين والتسوية
- شروط الائتمان وسياسة أعمار الديون
- الشهر المالي: افتُرض شهريًا (YYYY-MM). إن كان للشركة تقويم آخر يُعدَّل في `fiscal_periods`.

## التقارير

`trialBalance()` يقرأ من القيود المُرحَّلة مباشرة — صحيح وبسيط، لكنه يمسح كل قيود المدى. عند نمو الدفتر، أول تحسين هو جدول أرصدة مُجمَّعة (materialised balances) يُحدَّث مع كل ترحيل. لا داعي لبنائه الآن.
