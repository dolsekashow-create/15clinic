# التشغيل والنشر — من صفر لنظام شغّال

الترتيب ده مقصود. متتخطاش خطوة، خصوصًا القسم ٦.

---

## 1. حسابات وأدوات (مرة واحدة)

| الأداة | الغرض | ملاحظة |
|---|---|---|
| Firebase project | Auth + Firestore + Storage | أنشئ مشروعين: `clinic-staging` و`clinic-prod` |
| GitHub repository | الكود | **Private** |
| Vercel | استضافة الويب | يربط بالـrepo |
| دومين | العنوان | مثال: `clinics.com` للموقع و`app.clinics.com` للوحة |

**مشروعان منفصلان في Firebase ليس رفاهية.** أي تجربة أو Seed على قاعدة بيانات فيها بيانات مرضى حقيقيين = كارثة لا يمكن التراجع عنها.

---

## 2. إعداد Firebase

في مشروع الإنتاج:

1. **Authentication** → فعّل Email/Password فقط في البداية. (Phone لاحقًا لتطبيق العميل.)
2. **Firestore** → أنشئ قاعدة في وضع **Production mode** (يبدأ برفض كل شيء)، والمنطقة `europe-west` أو الأقرب لمصر.
3. **Storage** → نفس المنطقة.
4. **Service Account** → Project settings ← Service accounts ← Generate new private key.
   الملف ده = مفتاح كل حاجة. **متحطهوش في المستودع نهائيًا.** افتحه، خد منه ٣ قيم فقط، وامسحه من جهازك.

---

## 3. متغيرات البيئة

```bash
cp .env.example .env.local
```

القيم المطلوبة:

| المتغير | من فين | حساس؟ |
|---|---|---|
| `NEXT_PUBLIC_FIREBASE_*` | Project settings ← Your apps ← Web app | لا (عامة بطبيعتها) |
| `FIREBASE_PROJECT_ID` | ملف الـservice account | لا |
| `FIREBASE_CLIENT_EMAIL` | ملف الـservice account | لا |
| `FIREBASE_PRIVATE_KEY` | ملف الـservice account | **نعم — سري تمامًا** |
| `FIREBASE_STORAGE_BUCKET` | إعدادات Storage | لا |

`FIREBASE_PRIVATE_KEY` يُلصق كسطر واحد مع الإبقاء على `\n` كنص حرفي.

في Vercel: Settings ← Environment Variables، وحدد لكل متغير البيئة (Production / Preview / Development). **علّم `FIREBASE_PRIVATE_KEY` كـSensitive.**

> لو المفتاح اتسرب في أي وقت: Firebase Console ← Service accounts ← احذف المفتاح القديم وأنشئ جديد. التسريب مش بيتصلح بتغيير الباسوردات.

## 4. نشر القواعد والفهارس

```bash
npm i -g firebase-tools
firebase login
firebase use --add        # اختر مشروع الإنتاج
firebase deploy --only firestore:rules,firestore:indexes,storage:rules
```

من غير الفهارس، استعلامات الدور والفواتير هتفشل. من غير القواعد، قاعدة البيانات مفتوحة.

---

## 5. أول تشغيل

```bash
pnpm install
pnpm --filter @clinic/seed start     # على staging أولًا
```

الـSeed بينشئ: المؤسسة، ٣ فروع، ٦٥ صلاحية، الأدوار المبدئية، شجرة الحسابات، وحساب Super Admin.

على الإنتاج: شغّل الـSeed **مرة واحدة فقط**، وبعدين احذف `SEED_SUPER_ADMIN_PASSWORD` من البيئة.

```bash
pnpm build
vercel --prod
```

## 6. تأمين ما قبل الإطلاق — إلزامي

- [ ] `.env*` مش مرفوع (`git log --all --full-history -- .env*` لازم يرجع فاضي)
- [ ] لو أي secret اترفع في أي commit قديم → **دوّره فورًا**، الحذف من التاريخ مش كفاية
- [ ] المستودع Private، وBranch protection على `main`
- [ ] Firestore rules منشورة وواقفة على deny-by-default
- [ ] Storage rules منشورة (لا bucket عام)
- [ ] لا يوجد `NEXT_PUBLIC_` أمام أي مفتاح خادم
- [ ] Super Admin عليه كلمة مرور قوية + **2FA على حساب Google المرتبط**
- [ ] كل موظف له حساب باسمه — **ممنوع حساب مشترك للاستقبال**
- [ ] الدومين على HTTPS مع HSTS (مضبوط في `next.config.ts`)
- [ ] فعّل **Firebase App Check** قبل إطلاق تطبيق العميل
- [ ] Firestore backup: Console ← Firestore ← Backups ← جدولة يومية، احتفاظ ٣٠ يوم
- [ ] جرّب **استرجاع** نسخة على staging مرة واحدة على الأقل. نسخة احتياطية غير مُختبرة ليست نسخة احتياطية.

## 7. تشغيل يومي لصاحب الشركة

**اليوم الأول — إعداد الهيكل (نصف يوم):**

1. ادخل بحساب Super Admin.
2. الفروع والأقسام: عدّل الفروع التجريبية لأسماء وعناوين فروعك الحقيقية، أو أضف الـ15.
3. المستخدمون: أضف مدير كل فرع، وحدد له **الفرع/الفروع** اللي يشوفها. المستخدم لا يرى أي بيانات خارج فروعه، والفرض على الخادم لا في الواجهة.
4. الأدوار: راجع مصفوفة الصلاحيات. الأدوار المبدئية اقتراح للبدء وليست قرارًا نهائيًا.
5. الأطباء والخدمات: أدخل الأسعار الحقيقية.
6. المخازن: أنشئ مخزن لكل فرع، وأدخل الأصناف وأرصدة أول المدة كـ«استلام».
7. المحاسبة: راجع شجرة الحسابات مع المحاسب قبل أول فاتورة. تغيير شجرة الحسابات بعد آلاف القيود مؤلم.

**التشغيل اليومي:**

| الدور | الشاشة |
|---|---|
| الاستقبال | «الاستقبال والدور» — تسجيل حضور، نداء، انصراف، إصدار فاتورة وتحصيل |
| مدير الفرع | «نظرة عامة» — الانتظار، متوسط الانتظار، أصناف تحت حد الطلب |
| المحاسب | «الفواتير والتحصيل» ثم «القيود والتقارير»، وإقفال الشهر |
| صاحب الشركة | «سجل العمليات» — من عمل إيه وإمتى، على مستوى كل الفروع |

**آخر كل شهر:** المحاسب يراجع ميزان المراجعة ثم يقفل الفترة. بعد الإقفال لا يمكن الترحيل داخلها إلا بفتحها من جديد وده مسجّل في سجل العمليات.

---

## 8. حدود لازم تعرفها

- الحماية من التسريب داخليًا تعتمد على أن **كل موظف له حساب باسمه**. الحساب المشترك يُبطل سجل العمليات بالكامل.
- Rate limiting مش متفعّل بعد — الـinterface جاهز والمزوّد لسه محتاج قرار (Upstash Redis أو عدّاد Firestore).
- 2FA لحسابات الإدارة داخل النظام نفسه لسه مش متنفّذ.
- الكود اتكتب لكن **متجربش على مشروع Firebase حقيقي بعد** — لازم دورة `pnpm install` وتشغيل فعلي على staging قبل أي إطلاق.
